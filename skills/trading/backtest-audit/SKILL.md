## When to Use

当用户要求独立复算、审查回测、核对反事实规则、解释不同延迟/边界结果，或验证场景与真实 ledger 对齐时使用。尤其适用于“脚本显示 PASS 但需要判断是否真的可信”的情况。

用于审查交易策略回测、反事实回测和风险管理规则的实现与结果。目标是区分“程序成功运行”与“模型足以支持结论”，不得把报告自报的 PASS 当作审查结论。

## 核心原则

1. **只读审查优先**：除非用户明确要求修复，不修改代码、输入 JSON、交易系统或运行状态。
2. **独立复算**：不能只运行原脚本或复述报告；从输出 JSON 重新聚合逐笔结果，并尽可能用独立逻辑重算总 PnL、最大回撤、触发数、退出数。
3. **逐笔而非只看汇总**：比较场景时核对每笔 ID、退出原因、退出时间、fill 事件、价格、数量和 PnL。
4. **声明精确边界**：最终汇总相同不等于逐笔内部状态完全相同；浮点近似相同不等于原始字段相同。
5. **PASS 分层**：分别给实现逻辑、数据对齐、算术复算和方法学有效性结论；若存在费用、MTM、时间序列或同分钟假设局限，整体只能给 CONDITIONAL PASS 或 FAIL。

## 标准流程

### 1. 定位输入、实现和产物

找到：

- 回测入口脚本和被调用模块；
- 原始/缓存行情 JSON；
- ledger、CURRENT 或 userTrades 派生数据；
- 结果 JSON、Markdown 报告和测试文件。

先读取实现和结果，再运行回测。记录运行是否成功，但不要把 exit code 0 当成正确性证明。

### 2. 检查规则实现

逐项对照用户描述和代码：

- **R 口径**：明确 entry、initial SL、方向符号、触发价格和是否使用实际成交价；
- **同分钟不可追溯**：本分钟开始时保护状态是什么；同一根 K 线先触发阈值后回撤是否被错误追溯；
- **延迟**：delay=0 是否仍有明确的同分钟顺序假设；2/3 分钟是否真正影响保护生效时间；
- **TP1 后减半**：TP1 命中数量、剩余数量、TP2/BE 顺序和 step size 取整；
- **费用**：入场、每次退出、TP1/TP2/SL/BE、funding 是否分别计入，场景与 CURRENT 是否同口径；
- **生命周期 MTM**：估值时点是否严格早于 cutoff，剩余仓位是否清零，是否错误收取或遗漏假设退出费；
- **数据窥视**：是否使用 entry 之后且符合截止时间的数据，是否把 future bar 用于当前决策。

### 3. 独立从 JSON 复算

使用独立脚本或一次性审计脚本：

- 读取所有 scenario rows；
- 按场景 `sum(net_pnl)`；
- 按退出时间排序累加净 PnL，计算峰值回撤；
- 统计 settled/MTM/unsettled；
- 统计 `be_armed`、提前 BE 退出、TP1 命中及各退出原因；
- 将独立值与 JSON summary 比较，给出容差和差异行。

不要手抄多币种表格；让脚本输出原始表格或结构化结果。

### 4. 场景逐笔差异分析

对“只改变退出规则”的单变量反事实（如 TP1 全仓退出），先把语义钉死并分开报告：

- **可实现路径反事实**：真实入场/数量不变；TP1 先触发则全仓退出，SL 先触发则止损；生命周期截止仍未触发则 MTM。
- **全样本强制按 TP1 成交**：包括历史上从未触及 TP1 的交易，只能作为事后理论上限，不得称为路径回测或可实现收益。
- 反事实与 CURRENT 必须使用完全相同的 ledger ID 集合；结果至少并列报告总净 PnL、胜率、最大回撤、差额、TP1/SL/MTM 数量，以及剔除最大贡献单后的敏感性。
- 如果 MTM 占比较高，结论必须降级并明确说明：这些不是已实现退出，不能据此直接修改实盘规则。

对每一组阈值分别比较 bound 和 delay。至少比较：

```text
(id, exit_reason, exit_time, net_pnl,
 fills[event,time,fill_price,qty])
```

同时做完整字段差异检查，尤其是：

- `be_trigger_time`；
- `be_active_at`；
- `ambiguous_minutes`；
- fill 时间和生命周期 market bar 时间。

报告：

- 汇总值是否相同；
- 完整逐笔签名有几个等价组；
- 差异是否只是内部状态/浮点误差，还是改变成交路径或财务结果；
- 同分钟 ambiguous 是否真实发生，而不是因为统计字段永远未被触发。

### 5. 母体和 CURRENT ledger 对齐

核对：

- 母体数量是否等于要求的数量；
- CURRENT contributions 数量；
- 两边 ID 集合是否完全相等；
- 是否有重复 ID、缺失 ID、多余 ID；
- CURRENT ledger 独立求和是否等于 CURRENT 总额；
- CURRENT 的费用、funding、realized PnL 来源是否真实且与场景可比。

输出缺失/多余集合，即使为空也要明确写出。

### 6. 重大局限检查

至少审查并明确标注：

- 生命周期 MTM 是否没有假设退出费；
- scenario 模型费率是否与真实 commission 不同；
- funding 是否缺失或只在局部 artifact 中存在；
- 1 分钟 OHLC 无法确定同分钟先后顺序；
- 最大回撤是逐笔退出权益 DD 还是逐分钟/逐 tick MTM DD；
- 未结仓位、重叠持仓、资金占用和组合层面回撤是否被忽略；
- 反事实规则是否使用了事后可知信息；
- 样本是否只有单一市场阶段或样本量不足以支持规则生效。

## 输出格式

中文、直接、先结论后证据：

```text
总判定：PASS / CONDITIONAL PASS / FAIL
运行验证：
逐项规则审查：
独立复算：
场景逐笔差异：
63笔/当前账本对齐：
重大局限：
最终是否足以支持采用：
```

不要先写长篇计划；用户要求继续时直接执行检查。若用户表现出不耐烦，避免解释无关 skill 或重复前情，只报告已执行动作、证据和判定。

## 可复用支持文件

- 逐笔场景比较与 JSON 聚合脚本应放在 `scripts/`；
- 具体某次回测的差异、数据快照和复现命令应放在 `references/`，不要塞进主 SKILL.md；
- 任何支持文件都必须说明其是否只读、输入路径和核对容差。
