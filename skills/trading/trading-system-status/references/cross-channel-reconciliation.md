# 跨窗口结论对照：2026-08-16 完整案例

## 场景

用户两个 TUI 窗口相隔约 1 小时各跑一次扫描。窗口 B 报告"无达标候选 0 计划"，用户发现与窗口 A 结果不同，要求对比。

## 两边事实

- **窗口 A**（08:58 扫描，session `20260815_203611_eb8be8`）：大盘空头抬头。建 NEAR 反抽空（触发 1.622 反抽受阻回落 / 止损 1.634 / TP1 1.581 / TP2 1.536，3.4R）+ DOGE 反抽空（0.0697 / 0.0701 / 0.0687 / 0.0676，2.5R）两个 plan 并上 Cron；09:51 用户要求删除两计划（五样全清）。
- **窗口 B**（10:03 扫描）：大盘同样判空。NEAR/DOGE/SUI 等全部淘汰，0 计划，只给 WATCH_ONLY 复查条件。

## 根因三分类（对照框架）

1. **行情位移**：NEAR 15m RSI 24.9→22.5、价格 1.613→1.607；DOGE 未反抽仍阴跌。同一禁手判定（追地板/R 挤压）两边一致，变的只是深度。
2. **会话隔离**：窗口 B 不知道窗口 A 在 09:51 删过 NEAR/DOGE 计划——memory/技能跨会话共享，聊天记录不共享。向用户如实说明"当时不知道"，不装作知道。
3. **窗口 B 漏了评估档**：只验了"直接破位空"（触发=破前低），被禁手挡后直接淘汰；没有像窗口 A 那样补验"反抽空"方案档（SUI 反抽空事后验算 1.37R 其实是达标的）。当场承认，不辩护。

## 处理与结果

- 并排对比表 + 三因归因 + "确定性规则两边一致=不是系统 BUG"的证据式安慰
- 用户拍板"这轮轮空"。用户明确拒绝把"必须补验反抽空档"写进候选筛选技能（保持现状）——**尊重此决定，勿再写**
- 下一轮（11:02 扫描）主动把反抽空档纳入验算：KAITO 直接破位空被超卖禁手挡（4h RSI 14.9）→ 反抽空档数值 1.65R 但风险结构差（费率 -0.00068 负 + TP1 对齐的历史新低 0.3482 下方真空）→ WATCH_ONLY；HYPE 突破多达标（1.71R）建计划。

## session_search 检索技巧

- 发现：query="扫描 计划 达标" / "扫描 机会 计划"，`sort=newest`；browse（无参数）列最近活跃会话
- 定位后：`session_search(session_id=..., around_message_id=...)` scroll，window 12-20 逐段还原 plan 表格与删除动作
- 超大结果会持久化到 `/tmp/hermes-results/<call_id>.txt`（130KB+ 会触发）；用 `python3 -c "import json; ..."` 提取 user/assistant 的 content 摘要，只打印前 500 字符/条，避免全量灌进上下文
- 关键线索词：另一窗口的 plan 文件名（`NEARUSDT-plan.json`）、Cron job_id、消息 id 时间戳换算（epoch 秒 → CST）

## 边界提醒

- 对比时把"判定规则"和"输出结果"分开看：规则一致（禁手判定两边相同）而输出不同 → 输入变了或流程漏档，不是系统坏
- 用户跨端对照是主动兜底习惯，回答永远客观评估、非辩护；自己的漏档要放在归因第一位

# 08-17 补充：R 门槛口径不一致 + plan 溯源技巧

## 场景

状态检查发现持仓 HYPE 的 TP1 = 1.06R（低于 1.2R 门槛）。溯源后发现：同日 00:50 TUI 端因"R 结构 1.03R 不达标"否掉 WLD，而 12:16 微信端建 HYPE 时明确写"TP1 60.47（日线高，+1.98% = **1.06R ✅ 压线**）"放行——**同一套标准，两个窗口执行口径不一致**（1.06 算过、1.03 不算过）。用户当天即在微信端看着 HYPE 开仓，状态检查时主动报告此发现。

## plan 溯源方法（找到建 plan 会话 + R 计算原文）

1. **先算当前 R**：开仓后 plan 里 stop_loss/TPs 已是滑点校准写回值；等距平移使 R 不变，故当前 R = 创建时 R（HYPE：59.433/58.333/60.603 → 1.10 风险 / 1.17 收益 = 1.06R，与创建时 59.3/58.2/60.47 完全一致）
2. **复原平移前计划值**（备查）：执行日志"入场偏差检查通过: 偏差 X ≤ 止损距离 Y"→ 原止损 = 触发价 − Y；"滑点校准…平移 +delta"→ 原值 = 现值 − delta
3. `session_search(query=币名, sort=newest)` 发现 → 长会话（微信 session `20260721_231228_9f555b5c` 这类持续数月的）用 `around_message_id` 滚动，把 plan.created_at 换算 epoch 秒定位时间窗口
4. 创建原文在 `write_file(plan)` 前 1-2 条 assistant 消息里，含"关键位置：触发 / 止损 / TP1(xR 标注) / TP2"一行——R 当时算没算、标注什么结论（"✅ 压线"/"不达标"），一目了然
5. 复算核对：止损距离 = 触发价 − 止损；TP1 R = (TP1 − 触发) / 止损距离

## 两种读法（都摆给用户，由用户定统一口径）

- **机械门槛**：TP1 ≥ 1.2R → HYPE 1.06R 不达标（同日 WLD 1.03R 被否用的就是这条）
- **ZEC 先例**（"TP1 对齐第一阻力非机械 1.2R"）：突破类 TP1 对齐阻力时，下限 = TP1 距 > 止损距（R>1.0）→ HYPE 1.17 > 1.1 压线合规

## 口径（本案例的说话方式）

- 持仓本身**无需任何调整**（SL/TP 正确在位、风控距离完好、reduceOnly 兜底）——问题在"建 plan 门槛"不在"持仓管理"
- 不自行替用户判定哪条对；若用户定死统一口径，写回 candidate-screening / trading-plan-format 并在下次建 plan 执行
- 报告顺序：系统健康 → 持仓+SL/TP 证据链 → R 事实 → 两种读法 → 余额闭合；R 问题只做事实陈述+溯源引用，不渲染成"系统故障"
