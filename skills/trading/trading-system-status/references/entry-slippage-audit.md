# 入场滑点审计：真实分布、根因分解、优化方向

用户问"滑点是不是有点大 / 能不能优化"时用。**禁凭印象回答，禁引用文档里的旧百分比** —— 先跑 `scripts/slippage_audit.py`。

## 一、真实分布（2026-08-25 首次全账本审计，62 笔开仓）

```
不利滑点(按多空方向校正,正=吃亏): 均值 +0.275%  中位 +0.165%
>0.7%: 10/62 笔    >1.0%: 4/62 笔    实际占便宜(负): 9/62 笔
最差 +1.78%(BEAT 07-31 long)   最好 -1.51%(BEAT 08-01)
折算 R(41 笔账本有 stop_loss+quantity)：均值 +0.177R 中位 +0.086R 最差 +0.720R
累计隐性成本 +7.27R ≈ 18.80 USDT（≈当时余额 92.74U 的 20.3%）
```

两个关键读数，缺一个就会误导用户：

1. **整体不大**：中位仅 0.165%，"滑点大"的印象通常来自最近几笔连击（08-24 LTC +0.90%、08-24 BTC +0.65%、08-25 XMR +1.21%）。
2. **但方向系统性偏不利**：53/62 笔在不利方向（随机应 ≈50/50）。所以不能说"随机波动、无需在意"——存在结构性成因。

⚠️ 必须按**多空方向**校正才叫"不利滑点"：做多成交更高=吃亏，做空成交更低=吃亏。只看 `滑点校准` 日志里平移量的正负号会把空单判反。

## 二、根因三段分解（2026-08-25 XMR 逐秒还原，方法可复用）

触发 436.0 → 成交 441.28（+1.21%），用 1m K 线把 5.28 的滑点拆开：

| 环节 | 时刻 | 价格 | 归因 |
|---|---|---|---|
| 15m K 线收盘确认 | 02:29:59 | 437.05 | 收盘价本身已超触发价 → **+1.05（20%）** |
| 监控 Cron tick 写事件 | ~02:31 | 440.54 | ↓ |
| 事件处理 Cron 市价下单 | 02:32:28 | 441.28 | **延迟漂移 +4.23（80%）** |
| 盘口吃单成本 | — | 441.28 落在 02:32 那根 1m 的 [440.48, 442.16] 内 | **≈0** |

延迟实测 **149 秒**（三跳：K 线收盘 → 监控 Cron 1m 粒度 0-60s → 事件文件 → 事件处理 Cron 1m 粒度 0-60s → 市价单）。那 3 分钟 1m 量能 49→497→427→288（10 倍放量拉升）。

**结论口径**：主因是 `require_close=true` 收盘确认制 + 两级 1 分钟轮询的固有节奏，**不是流动性、不是市价单、不是行情针对**。

复用方法：`api_get('/fapi/v1/klines', {'symbol':S,'interval':'1m','startTime':ms,'limit':10})` 取成交前后各几根 1m，看成交价是否落在当根 K 线区间内——落在区间内即证明吃单成本≈0，滑点全来自延迟。

## 三、平移的第二层代价：止损位从"结构外"挪进"结构内"

**这是 08-25 之前一直漏讲的**（旧文档只说"等距平移→R 不变→结构完好"就收尾，被用户追问优化时才发现不完整）。等距平移确实保住风险额和 R 倍数，但：

1. **目标位被推高**：XMR TP1 从 466.40 → 471.68。若行情只到 469，原计划早止盈，平移后拿不到。
2. **止损位失去结构保护**：XMR 原 SL 424.50 设在 15m 支撑**下方**；平移后 429.78 站到支撑**上方 5.28**，已在结构内部。正常回踩到真支撑 424-425 再起涨会被扫掉，原计划不会。
3. **invalidation 线不随平移**：plan 的 `invalidation_4245` 仍是 424.5 → SL(429.78) 必然先于"逻辑失效"触发，失效线永远等不到。

回答用户时这三条要跟"R 不变"一起说，别只报喜。

## 四、优化方向清单（2026-08-25 已向用户列出，**全部待拍板、零改动、未生效**）

用户当轮明确"只说方法先别改任何东西"。以下均为**建议**，勿自行实施。

### A 压缩延迟（治 80% 主因，不改任何决策规则）
- **A1 两级 Cron 1m→30s**：延迟上限 120s→60s，期望滑点砍半（≈9.4U/62 笔）。**前置待验证：Hermes Cron 是否支持 30s 粒度**；不支持则退化为包装脚本内 `sleep 30` 跑第二遍（纯 bash 加法，不碰 Python）。API 频次翻倍（币安权重充裕）；signal_monitor 有 state 去重，30s 内不会重复触发。→ 推荐优先级最高的代码类改动
- A2 包装脚本写完事件立刻调 `process-events` 省第二跳：**有并发风险**——与事件处理 Cron 同秒都可能查到"无持仓"→ 双开仓，必须加文件锁。参见 `event-write-vs-process-race-20260824.md`
- A3 systemd timer 对齐 K 线边界（:00/:15/:30/:45 +2s/+5s），延迟压到 10s 内，但脱离 Hermes Cron 体系（与"长期监控必须走 Hermes Cron"的既有教训冲突）

### B 给滑点封顶（宁可不成交）
- B1 入场市价单→LIMIT+IOC，限价=触发价×(1±0.4%)：硬顶滑点，代价=加速突破直接不成交（XMR 那单就不会开，而它开出来是浮盈的）
- B2 收紧偏差门（现阈值=1 个止损距离，改 0.5R 或 0.5% 取小）：**必须先用 41 笔账本回测**，见 `rule-backtest.md`（08-10"弱市禁多"就是被回测否决的）

### C 零代码，只改建 plan 口径（可立即采用）
- **C1 R 预检预扣滑点**：算 R 时用「预期入场 = 触发价 ×(1+0.28%)」（实测均值），R 不达标就不建 → 把滑点成本前置进筛选
- C2 触发价避开整数关口 / 24h 高点正上方 1 tick（抢单最密集处）
- C3 突破前 1m 已 10 倍放量的（XMR 型），预判滑点大，TP1 主动拉远补偿

### D 改仓位算法（治第二层代价，改动面最大）
- D1 滑点大时不做等距平移、保留原结构止损，改按结构止损反推数量（XMR：`qty = 2.6U ÷ 16.78 = 0.155`，名义 68U）。风险额不变、结构位不失守，代价=仓位变小且会撞名义价值偏差门（±25%），需同步调整

**推荐顺序**：C1（零风险零代码）→ A1（先验证 Cron 粒度这一纯查询动作）→ B2（须先回测）→ A2/A3/B1/D1 暂缓（触碰执行链，风险>收益）。
