# 流程完整性质疑后的补验标准动作(2026-08-21 实例)

用户问"这次挺快,没偷懒/跳过环节吧?"时的处置实例。主链路 10 环节全部有产出物时间戳(扫描文件名、fetch_klines"分析时间"、dry-run UTC 时间戳、Cron ID、plan mtime),但**真漏了一处**:trade-execution-planner 的 `references/execution-rules.md` 当时未显式读(plan 参数照 DOT 历史模板+plan-format 规范生成)。

## 补验标准动作(可复用)

1. **当场承认漏读**,不混在"速度快"里蒙混。
2. **当场补读**漏掉的参考文件。
3. **逐条对照规则文件验证已生成 plan 的每个参数**,每处差异写明依据 + 重算 R,全部列表给用户:

| 参数 | 已生成 plan | 规则要求 | 差异处置 |
|---|---|---|---|
| 触发缓冲 | 0.6810(前高本身) | 阻力+0.2×ATR=0.6819 | require_close 收盘确认替代缓冲,DOT 历史模板同款;按 0.6819 重算 R 1.36→1.25 仍达标 |
| 止损缓冲 | 0.6630(1h 双K低点 0.6634/0.6635 下方) | 0.50×ATR15m→0.6612 | 结构位优先于 ATR 缓冲;更紧="被扫即证伪点更快"的设计内代价(SUI 8-17 先例) |
| TP/order/cancel | 合规 | — | TP 用 R 倍数(上方真空)、STOP_MARKET、invalidation<止损,逐项确认 |

4. **时间线证据表**:每一步 → 时间戳(如 08:31 启动检查 / 08:32 扫描 JSON fetchedAt / 08:32:59 fetch_klines / 08:45 plan created_at / 08:37 dry-run / 08:38 Cron ID)。
5. **速度合法来源**:并行扫描 74 币、refs 在扫描等待期加载、fetch_klines 3 币 15 秒、环节间零等待;同会话已加载过的技能/refs 可复用(省读取时间非分析环节)。
6. **用旧数据要说明**:启动前检查的 Cron 列表若用几分钟前刚查的结果(中间只发生过自己执行的删除),明说"新鲜度确定"。

## 教训

- 生成 plan 前,加载 trade-execution-planner 时必须同时读其 `references/execution-rules.md`(SKILL.md 第 4 步明示)——这是历史上真实的跳步点。
- "快"引发质疑时,用户要的是证据链,不是保证;证据=产出物时间戳+逐项对照。
