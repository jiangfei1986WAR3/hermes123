# 触发价 vs 成交价偏差解释（用户质询应对）+ 08-24 推送范围教训

两个本会话实战模式，一个回答话术、一个流程纪律。

## 1. 用户问"成交价比触发价高这么多，系统允许吗？正常吗？"（08-24 BTC 例）

实例：BTC 突破计划触发价 77591，15m 收盘 07:30 确认（C=77642），07:34:02 市价成交 **77688.1**，偏离 +97.1U（0.125%）。用户质询后按四件套回答，用户认可：

1. **机制**：STOP_MARKET = 触发后按当时市价成交，触发价是保险丝不是价格承诺。
2. **时间链**：15m 收盘确认（require_close，用户自选设计）→ signal_monitor Cron 检测 → 事件处理 Cron 执行，链路延迟 2-4 分钟，期间价格继续涨——这是"收盘确认换假突破过滤"的固有权衡，不是故障。
3. **允许边界**：executor 偏差门=现价偏离触发价 ≤ 止损距离才放行。本次偏离 102.3U 只占上限（821U）的 12.5%；超限会被拒（防暴涨追高）。日志证据：`✅ 入场偏差检查通过: 偏差 102.3 ≤ 止损距离 821`。
4. **风控不缩水**：滑点校准等距平移（SL/TP 全部 +97.1），止损距离 821 不变、R 1.51/2.39 不变、风险额 2.12U 不变。

偏离 0.125% 属低位（62 笔实盘不利滑点中位 0.165%、均值 0.275%，见 `references/entry-slippage-audit.md`；旧文档"常见 0.3-0.7%"已作废）。附 K 线时间戳列表 + 日志偏差行当证据，勿空口说"正常"。

## 2. 推送范围=用户授权语境（08-24 流程教训）

用户说"这次修复确认后推" = 授权语境是"这次修复"，**不等于**授权"上次推送以来的全部积压"。08-24 把积压一周的内容（新监控脚本 btcusdt-monitor-check.sh + 27 篇实战文档 + BTC plan 快照）打包同一 commit 推了，用户质问"这是什么？怎么把这个推上去了？"。正确做法：

- 授权语境窄时，推送范围限于语境内内容；其余积压即使按三档分类属于"必推"档，也**先列清单给用户过目等确认再推**（用户说"推"≠"推全部"）
- 要一起推则分开 commit、汇报里明示每部分归属（回滚点逐块可追溯）
- 被质问后如实交代"是什么+为什么进清单+认范围错误"，给处置选项（保留/撤销/用户点菜）让用户拍板；用户说"算了无所谓"后不再自行"补救性重推"
- 回滚点汇报：修复前快照 commit hash + 本次 commit hash
