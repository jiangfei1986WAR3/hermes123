## 一、30s 粒度：不支持（三层硬证据，勿再当待验证项）

1. **解析器无秒单位** — `cron/jobs.py: parse_duration()` 正则 `^(\d+)\s*(m|min|...|h|hr|...|d|day...)$`，`multipliers = {'m':1,'h':60,'d':1440}`。实测 `'30s'` / `'every 30s'` / `'every 0.5m'` 全部 `ValueError`（连小数都不收）。
2. **6 字段 cron 能过解析但没用** — `'0 * * * * */30'` 被 croniter 接受，`compute_next_run` 真能算出 30 秒后的 next_run。然而……
3. **ticker 60 秒是物理下限** — `cron/jobs.py:99  TICKER_INTERVAL_SECONDS = 60`；实测心跳周期 **60.07s**（`~/.hermes/cron/ticker_heartbeat` mtime 采样：07:58:13.233 → 07:59:13.279 → 08:00:13.366）。全代码库仅 1 处定义 + 1 处引用（CLI 算 staleness 阈值），**无配置项可覆盖**。每个 tick 最多点火一次 → 有效频率上限就是 60s。

→ 想要秒级只能改源码常量，而 Hermes 是 git 安装，升级即被覆盖。**这条路已封闭。**

## 二、更重要的发现：`every 1m` 实际跑 120s（确定性 2 倍空转）

两个 job 各 20 次运行，**间隔全是 120s，无一例外**。心跳与点火对齐即铁证：

```
● 07:58:13.233 心跳    ✓ 07:58:13.216 事件处理   ✓ 07:58:13.223 XMR监控
● 07:59:13.279 心跳    ——— 两个 job 都没点火 ———   ← 整轮空转
● 08:00:13.366 心跳    ✓ 08:00:13.290 事件处理   ✓ 08:00:13.356 XMR监控
```

**根因是 0.4 秒的锚点错位**：

| 环节 | 实测 |
|---|---|
| `compute_next_run` 对 interval 型 | `next_run = last_run_at + 60s` |
| 但 `last_run_at` 记的是**执行完成**时刻 | 点火 `08:00:13.290` vs jobs.json `last_run=08:00:13.840` → **晚 0.55s** |
| 于是 next_run | `08:01:13.840` |
| ticker 每轮只多走 0.07s，下一 tick 落点 | `08:01:13.4x` |
| 判定 | `13.4x < 13.840` → **差 0.4s 未到期 → 跳过** → 再等 60s |

每轮都稳定差这 0.4 秒，所以是 **100% 必然空转，不是偶发抖动**。这就是旧文档 `event-write-vs-process-race-20260824.md` 里"1m 配置≈实际 2 分钟"那句现象描述的根因。

生活化解释（用户偏好类比）：闹钟每 60 秒响一次，但你起床后要花 0.55 秒才写好"下次 60 秒后"的便签 —— 下次闹钟响时便签时间还差 0.4 秒没到，你翻身继续睡，于是变成两分钟起一次床。

## 三、入场链路延迟预算

旧口径（按配置值算 0-120s）是错的。两段真实预算：

```
【修复前 每 1m】监控跳 0~120s + 事件处理跳 0~120s = 0~240s，期望 ~120s
                （08-25 XMR 实测 149s，正好落在此区间 → 滑点 1.21%）

【修复后 * * * * *，2026-08-25 08:43 起】← 讲现状用这个
                监控跳 0~60s + 事件处理跳 0~60s = 0~120s，期望 ~60s
```

讲滑点根因时：**讲历史案例（08-25 02:32 XMR 那笔及之前）用 240s/120s；讲当前系统用 120s/60s。** 别再说"两级 1 分钟轮询 0-120s"（那是按配置值的错算法）。

## 五、复查方法

- 一键探针：`scripts/cron_cadence_check.py`（对齐 run 历史间隔 + 心跳周期，直接给出"配置 vs 实际"倍数）
- 手工：`hermes cron runs <job_id>` 看时间戳间隔；`~/.hermes/cron/ticker_heartbeat` mtime 采样看 ticker 周期
- ⚠️ **测 Hermes 内部模块必须用它自己的解释器** `/usr/local/lib/hermes-agent/venv/bin/python`。系统 `python3` 缺 croniter，会误得出"cron 表达式不可用"的错误结论（08-25 本人踩过，当场向用户纠正）。`hermes` 是 bash wrapper，真解释器在 `venv/bin/`。
