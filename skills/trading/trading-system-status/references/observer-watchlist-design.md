# 观察列表方案（2026-08-07 探讨，未实施、未写代码）

用户认可方向：**每小时自动扫描 → 更新 `watchlist.json` 观察列表 → 单个聚合哨兵 Cron 盯所有观察位**。替代"每候选一个独立哨兵脚本+Cron"（会堆积膨胀）。落地前需用户确认；本文件是设计蓝图，不是已运行的功能。

## 为什么是这个形态（用户探讨结论）

- 15-30 分钟扫描频率对"发现"无帮助：格局 4h 节奏，横盘币（PAXG 例横 11 小时才突破）1-2 小时扫一次信息量相同，token 成本 1/4。用户拍板：**每小时**。
- 独立哨兵按候选堆积（一周几十个脚本+Cron）→ 改为**一个列表文件 + 一个聚合 Cron**，状态天然去重、可淘汰。
- 每小时扫描更新用**脚本+硬规则**（不用 AI）：入列标准可规则化（分数/涨幅/特征），零 token、零上下文断裂；AI 判断保留在"触发通知→用户叫我复查"一步。
- 形态：PY 文件放 `~/.hermes/scripts/`（Cron no_agent 调度，同 executor 套路）+ 简短 SKILL 说明书（AI 操作手册：怎么读/怎么手动加删/触发后衔接）。

## 组件

```
① watchlist.json         观察列表（唯一状态文件）
② watchlist-check.py     聚合哨兵（every 1m, no_agent, deliver=all）
③ watchlist-update.py    每小时扫描更新（每小时, no_agent, 完全静默无输出）
```

watchlist.json 条目：
```json
{"symbol": "PAXGUSDT", "watch": 4317, "side": "above",
 "note": "黄金突破4300观察，到了复查", "added_at": "08-07 09:00",
 "expires_at": "08-09 09:00", "reset": 4250, "notified": false}
```
- `notified` 防重复通知；价格回落跌破 `reset` 重新武装
- `expires_at` 默认 48h 淘汰

## 与执行链路的关系（关键边界）

- **完全独立**：不写事件文件、不 import executor，物理上不可能下单（同现有哨兵）
- **唯一接触点**：更新列表前**只读** `~/.hermes/trading-plans/` 做冲突检查——该币已有 plan 或已持仓 → 不加
- **触发衔接**：哨兵通知 = 提醒复查，不是开仓。用户回"看看 XX" → 正常流程（fetch_klines → trading-analysis → 建 plan → dry-run 验证 → Cron）→ 转 plan 后从列表移除

## 扫描后候选三分类（决定谁进列表）

| 状态 | 处理 | 进列表？ |
|---|---|---|
| 现在就适合交易（触发/止损/TP 全清晰） | 直接建 plan（signal_monitor 自动执行） | ❌ |
| 做不了但值得等（超买等回踩/横盘等突破/超卖等反抽） | 进观察列表 | ✅ |
| 不值得关注（追高/追空镜像/R 差/空间不足） | 排除 | ❌ |

## 待定规则（落地前用户拍板）

1. 列表上限：建议 10（满了先淘汰失效）
2. 入列标准：分数 ≥60 + 24h 涨跌幅 <15% + 等触发特征（超买/横盘/贴关键位）
3. 淘汰：48h 过期 + 偏离观察位 >8% 自动删 + 上限满删最老
4. 通知格式：`「观察位触发」PAXG 4317.0（现价 4348.2）备注：…建议复查`

## 真实案例对照（验证设计合理性）

- ADA 14:10：位置干净 → 直接建突破 plan，不进列表 ✓
- ENA 17:05：突破后过热但回踩条件明确 → 直接建 pullback_reclaim plan（有明确触发要素，也不需要列表）✓
- PAXG 09:00：超买横盘、plan 要素不齐（"突破 4317 要看看"但止损/TP 未定）→ 列表候选 ✓（20:00 突破，若哨兵在位能抓住）
- CYS/ONDO：追高/超卖 → 排除 ✓
