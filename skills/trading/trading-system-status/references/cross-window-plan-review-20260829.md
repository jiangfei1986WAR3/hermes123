# 跨窗口 plan 复核：SOL 2026-08-29 案例

用户让本窗口复核另一窗口（TUI session 20260829_100552，glm-5.3-flash）建的 SOL 回踩多计划"是否合理"。复核结论：**基本合理，维持不动**。本文件存流程与三个可复用的复核发现。

## 定位建计划会话

- `session_search` query 用 **币名+触发价数字**："SOL 104.45 回踩 收复 做多 计划"（纯 "SOL 扫描 计划" 搜到的都是状态检查会话，加价格数字才命中建计划窗口）
- `sort=newest`，找到会话后用 `session_search(session_id=..., around_message_id=<建计划时刻附近的消息id>)` scroll，读到建计划时的完整分析原文（含当时对其他候选的否决理由，可做跨窗口一致性核对）

## 独立复算五件套（禁照抄原窗口声称）

1. **fetch_klines**：现结构是否支持 plan 的逻辑（缩量回踩企稳、RSI 是否已从超买回落）
2. **resistance_above / support_below**：TP 锚是否真实 200 日簇。SOL 实测：ref 104.45 上方 = 0天前 104.55（弱档）、1天前 110.04、2天前 110.6（强阻力簇）→ TP1 110.04 锚真实 ✓
3. **userTrades 验模式5**：SOL 8-28 18:07 刚止损 -1.68U @ 104.81；现价 103.98 **低于**出场价 → "现价在出场价上方=追高接回"排除条件**不成立** → 放行，但复核报告中须提及"刚止损的币"作心理风险提示（知情不拦截）
4. **dry-run**：验证触发语义静默 + state 为 `{}`（从未触发）
5. **R/数量/风险额 Python 复算**：R=(110.04-104.45)/(104.45-102.1)=2.38 ✓；qty=100/104.45=0.957→0.96 ✓；风险额 0.96×2.35=2.26U ✓

## 三个可复用的复核发现

1. **TP1/TP2 落在同一阻力簇且距离 <1% = TP2 形同虚设**：SOL TP1 110.04 / TP2 110.6 只差 0.5%，同属 110 阻力带——TP1 减半后剩半仓只走 0.5%。不影响风控，属"不致命瑕疵，维持+告知"档。8-28 版 SOL 计划（109.7/110.6）同病，说明这是模型常见写法，复核时主动查。
2. **pullback_low 未被近期窗口触碰 = 等新回踩的保守语义**：回踩低 103.2 在近 5h（20根15m窗口）未被触碰（实际最低 103.58）→ had_pullback=False，触发语义="必须再回踩到 ≤103.2、再收复 104.45 才触发"。**直接放量涨过 104.45 不回头则计划永不触发**（这是 08-06 修复后的设计意图，非 bug），但复核报告必须让用户知道这个代价。
3. **原窗口的 ATR 缓冲表述可能对不上实际值**：原窗口写"止损 1.7x 15m ATR 缓冲"，按当前 15m ATR 0.373 复算实际 2.35/0.373=**6.3×**（缓冲比声称的更大=安全方向）。复核以自己复算的数字为准，不照抄另一窗口的声称值；发现表述偏差只报告，不据此改计划。

## 复算表输出格式（用户接受的样式）

瑕疵分级：致命=改或删计划；不致命=维持+告知。默认不动另一窗口的 plan，除非用户明示。

## 同型再犯：TP 顺序写反（PENGU 2026-08-29 晚，本窗口自建自纠）

复核另一窗口时发现 TP1/TP2 同簇距离 <1% 的瑕疵后，**当晚本窗口自建 PENGU 反抽空 plan 时犯了姊妹错误**：`take_profits[0]` 写了远端 0.008774（1.63R）、近端 0.008832（1.34R）放第二位——TP 数组顺序=成交顺序，首位是移保本扳机，写反=近档先成交时移保本不触发、SL 留在原位。建完 Cron 自检时发现并 patch 换序。两条规则已分别升入 trading-plan-format（TP[0] 必须距触发最近：空=较高/多=较低，落盘前自检 `|TP[0]−触发| < |TP[1]−触发|`）。复核清单新增第四发现：**TP 数组顺序**（复核任何 plan 都查，本窗口自己写的也要查——同日两次教训说明这是系统性盲区，不是单次笔误）。
