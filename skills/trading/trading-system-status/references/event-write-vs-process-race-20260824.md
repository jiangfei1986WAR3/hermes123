# 事件写入 vs 处理轮竞态窗口（2026-08-24 实测）

## 现象

查状态时发现：事件文件（`BTCUSDT-TRIGGER-<epoch>.json`）存在，但 executor 日志无"处理触发事件"记录，事件处理 Cron 已跑过多轮。

## 根因

signal_monitor 写事件与 trading-cron 的 process-events 是两条独立 Cron 链，存在同秒级竞态窗口：事件写入可能晚于同轮 process-events 已跑完。

实测时间线（08-24 08:00 轮）：
- 08:00:05.617 — 该轮 process-events 开始（此时事件未写入）
- 08:00:05.788 — signal_monitor 写事件文件（比 process-events 晚 0.17 秒）
- 08:02:05 — 下一轮 process-events 才看到并处理事件（日志 `处理触发事件: BTCUSDT` → `已有持仓，不重复开仓` → 删文件）

## 判定与处置

1. "事件文件还在 + 日志无处理记录" = **窗口期内，属正常**，不是故障。事件最多滞留一个处理周期——**2026-08-25 起为 ≤60s**（schedule 改 `* * * * *`）；本文 08-24 时间线里的 2 分钟是当时 `every 1m` 的 2 倍空转所致（interval 型锚点错位，根因见 `references/cron-cadence-and-latency.md`），已修。
2. 判定前先对照时间戳：事件文件 mtime vs 最近一轮三步日志（process-events/manage/watch 各一条"运行模式"行）的时间，谁先谁后。
3. **勿手动 process-events**（会真下单）——等下一轮自然处理。有持仓时重复触发会被"已有持仓"安全门拦（开仓后冷却期 600s 过后价格再站上触发价的重复事件同理）。
4. 用户视角的"事件没被处理"应展示完整时间链证据（写入时间/处理轮时间/拦截日志），而不是报告"系统没处理事件"。

## 另一类"触发晚于预期"：缩量K线被弱保护跳过（08-24 BTC 例）

突破已发生但触发迟迟不来时，先查被跳过 K 线的量比：`min_volume_ratio=1.0` 会跳过缩量 K 线（防缩量破位），等下一根量比≥1.0 的收盘再触发。08-24 20:15 建 BTC 计划，20:00 K 线 C=78127 已在触发价上方但量比 0.87<1.0 → 跳过；20:15 K 线 C=78434 量比 1.06 → 20:31 写事件 → 20:33 成交。事件延迟=保护生效，不是故障；验证方法=拉 15m K 线算量比。
